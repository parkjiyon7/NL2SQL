어떻게 동작하나

  • watsonx Orchestrate(wxO)는 에이전트가 툴을 부르는 곳입니다. LLM은 호출 순서, 재시도, 답변 정리만 맡습니다.
  • watsonx.data intelligence(wxdi)는 데이터 설명서(카탈로그, 용어집)와 Text-to-SQL REST를 제공합니다. SQL을 만들기만 하고 실행하지는 않습니다. 프로젝트에 올려 둔 SQL 예시(few-shot) 17건 중 질문과 비슷한 3건을 프롬프트에 자동으로 넣습니다. SQL을 쓰는 모델은 wxdi 내부의 meta-llama/llama-3-3-70b-instruct(질문과 스키마를 맞추는 임베딩은 granite-embedding-278m-multilingual)이며, 응답의 resource_usage.model_usages에서 확인했습니다. 에이전트의 gpt-oss-120b는 SQL을 쓰지 않고 툴 호출 순서와 답변 정리만 맡습니다.
  • Db2는 데이터가 있는 곳입니다. 만들어진 SQL은 Db2로 직접 실행하며, 조회(SELECT)만 허용합니다.
  • QuickChart(외부 서비스)는 차트 이미지를 그려 주는 곳입니다. make_chart가 차트 값(라벨, 숫자)을 보내고 이미지 주소를 받습니다. 값이 이 서비스로 나가므로 실데이터에는 쓰지 않거나 자체 호스팅이 필요합니다.

SQL 품질을 지키는 장치

업무 용어와 조인 경로는 코드에 적지 않고 wxdi가 원본입니다. 툴은 읽어서 전달만 합니다.

  • 용어 정의 → Note: map_terms가 wxdi 용어집에서 읽은 정의(예: 거래대금 = EXECUTIONS.EXEC_AMOUNT)를 질문 뒤에 붙임
  • FK 조인 조건 → Note: generate_sql이 wxdi 카탈로그의 foreign_keys(join_condition)를 읽어 "이 조건으로만 조인하라"고 질문 뒤에 붙임. wxdi 제품은 FK를 LLM에 자동 전달하지 않기 때문입니다
  • few-shot 예시: 질문과 비슷한 SQL 예시(질문, 힌트, SQL) 3건을 wxdi가 프롬프트에 자동으로 넣음. 예시 17건은 wxdi 프로젝트에 올려 둔 CSV이고 툴 코드에는 없습니다(Few-shot 예시 (wxdi) 탭)
  • 연결 제한: 카탈로그에서 얻은 FIN_DEMO 연결 ID로 스키마 검색 범위를 제한
  • 고정 규칙 5개(instructions): 스키마 인용 규칙, 날짜(어제, 월), 대문자 식별자, 컬럼 한정, 숫자 단위(1억 = 100000000). Db2 문법과 한국어 표현만 두었습니다
  • fix_qualifiers: Db2가 거부하는 컬럼 한정 방식을 "FIN_DEMO"."T"."C" 형태로 자동 교정. 테이블 목록은 카탈로그에서 읽음

업무 용어와 동의어는 코드나 에이전트 지시문에 적지 않고 watsonx.data intelligence(wxdi) 비즈니스 용어집에 등록했습니다. 카테고리 에 표준 용어 개와 동의어 용어 개를 가져와 게시했고(wxdi 용어집에서 "약정", "업종 내 순위"를 조회해 게시된 것을 확인했습니다), map_terms가 질문을 받을 때마다 여기서 읽습니다. 용어를 고치거나 늘려도 툴 코드는 바뀌지 않습니다.

  • 정의에 컬럼명을 적어 둡니다: 정의 속 EXECUTIONS.EXEC_AMOUNT 같은 컬럼명을 map_terms가 읽어 "대응 컬럼"으로 돌려주고, generate_sql이 질문 뒤에 Note로 붙입니다.
  • 동의어도 하나의 용어입니다: "약정"은 별도 용어이며 표준 용어 "거래대금"에 동의어로 연결돼 있습니다. 질문의 "약정"을 찾으면 "거래대금"의 정의를 가져옵니다.
  • 같은 정의를 두지 않고 관계로 잇습니다: 관련 용어, 일부(예수금은 총자산의 일부), 하위 종류(지정가 주문은 주문의 한 종류)로 표시했습니다.

Text-to-SQL이 SQL을 만들 때 참고하도록 질문, 힌트, 정답 SQL 세트 건을 wxdi 프로젝트에 데이터 자산(text_to_sql_fewshots_0.csv)으로 올려 두었습니다. wxdi는 질문마다 이 중 비슷한 3건을 골라 프롬프트에 넣습니다(모델 입력 원문에서 확인). 에이전트 지시문이나 툴 코드에는 예시가 없습니다.

  • 어떻게 만들었나: 예시마다 SQL을 Db2에서 실제로 실행해 오류가 없는 것만 넣었습니다(option_b_watsonxdata/fewshots/build_fewshots.py). 힌트 열에는 용어 뜻, 조인 순서, 날짜 계산 같은 업무 규칙을 적었습니다.
  • 골든과 겹치지 않게: 골든 질문과 같은 문장을 넣으면 점수가 예시를 베낀 결과일 수 있어, 구조가 비슷한 예시는 값(종목, 지점, 숫자, 등급, 매수·매도)을 바꿨습니다.
  • 반영 방법: CSV를 프로젝트에 올린 뒤 온보딩 작업(Onboard for generative AI)을 다시 실행해야 프롬프트에 들어갑니다. 올리기만 했을 때는 들어가지 않았습니다.
  • 효과: 같은 데이터에서 골든 10문항 x 5회, 예시 있음 50/50(100%), 없음 45/50(90%)입니다. 문항별 비교는 이 탭 맨 아래 표에 있고, 단정하기에는 표본이 작습니다.
#예시 질문힌트 (evidence)SQL

이 표는 wxdi에 올린 CSV 원본에서 만들었습니다. wxdi를 실시간으로 읽는 화면은 아닙니다.

개인정보 마스킹은 에이전트가 쓰는 Python 툴이 아니라 watsonx Orchestrate의 내장 컨트롤 "PII Filter"로 처리합니다. 외부 소스나 별도 코드를 쓰지 않고 wxO 화면(Controls)에서 설정했습니다. 컨트롤 이름은 KR_PII_EMAIL_PN_SSN(내부 이름 test_email_control_6026oB)이고, Supervisor, 용어·메타데이터 검색, SQL, Insight 에이전트 4개에 연결했습니다. 마스킹 대상은 이메일, 휴대폰 번호, 주민등록번호 세 가지이며 고객 이름은 가리지 않습니다.

어디서 가려지나

  • 입력 훅과 출력 훅 둘 다: 에이전트가 받는 질문(agent_pre_invoke)과 에이전트가 내보내는 최종 답변(agent_post_invoke)에서 값을 찾아 바꿉니다. wxO 화면의 Enforcement type에서 Input과 Output을 모두 켠 설정입니다.
  • 답변 글자에 대해 동작: DB에서 읽은 값을 에이전트가 답변으로 쓴 뒤, 내보내는 단계에서 바꿉니다. 답변의 표에 나오는 값이 이 규칙으로 가려지는 것을 확인했습니다. 툴 호출과 DB 결과 단계에서 가리는지, 트레이스와 로그에 원본이 남는지는 확인하지 않았습니다.
  • 입력에서도 가림: 질문에 이메일을 적으면 SQL이 WHERE "EMAIL" = '**********'로 만들어졌습니다. 그래서 이메일 주소로 고객을 찾는 질문은 0행이 나옵니다.

  • 컨트롤은 사용자가 관리: 컨트롤은 사용자가 wxO 화면에서 만들고 고쳤습니다. 이 프로젝트의 API 키로는 컨트롤을 만들거나 고칠 수 없었습니다(관리자 권한 필요).

한계와 다음 단계

알려진 한계

  • 생성기의 비결정성: 같은 질문도 요청마다 SQL이 달라질 수 있습니다. 같은 구성으로 세 번 돌린 점수가 24/30, 24/30, 26/30이었고, 잔고 용어(예수금, 평가금액, 미수금) 정의를 보강한 뒤에는 27/30이었습니다. few-shot 17건을 넣은 구성도 한 번은 27/30(질문당 3번), 다른 한 번은 50/50(질문당 5번)이었습니다. 한 번의 점수 차이는 우연일 수 있습니다. 지금 가장 약한 질문은 30분 넘게 미체결인 주문(S3-04)으로, 예시가 없으면 "30분 안에 체결이 없는 주문"으로 해석해 행이 훨씬 많이 나오고, 예시가 있어도 가끔 열 이름의 따옴표가 어긋난 SQL 문법 오류가 납니다. 생성기가 용어 정의를 항상 따르지는 않아서, 같은 질문도 정의 문구에 따라 정상 비율이 달라집니다(VIP 예수금 질문 기준 정의 보강 전 6~8/10, 후 19/20).
  • few-shot의 효과는 방향만 확인: 같은 데이터에서 골든을 질문당 5번씩 돌렸을 때 예시 있음 50/50(100%), 예시 없음 45/50(90%)이었습니다. 차이는 대부분 S3-04(5/5 대 2/5)에서 났고, 같은 구성을 다시 돌리면 점수가 달라질 수 있어(예시 있음도 27/30이 나온 적이 있음) 효과가 있다고 단정하지는 않습니다. 예시 17건 중 10건은 골든과 구조가 비슷합니다(종목, 숫자, 등급 같은 값만 다르게 함). 구조가 다른 새 질문에서도 효과가 있는지는 시험하지 않았습니다. 예시를 고치면 CSV를 다시 올리고 wxdi 프로젝트의 온보딩 작업(Onboard for generative AI)을 다시 실행해야 프롬프트에 반영됩니다.
  • 복잡한 질의: 이전 값과의 비교(LAG), 이동평균, 상위 고객의 주력 종목처럼 CTE와 윈도 함수가 겹치는 질문은 오류가 나거나 질문의 일부만 답할 수 있습니다. 골든에 넣지 않았고 에이전트로는 다시 시험하지 않았습니다. 5개 테이블 JOIN, 서브쿼리, 비율 조건 질문(S3-01, S3-02, S3-05)은 이번 시험에서 정상이었습니다.
  • 개인정보: 생성기가 고객 목록 질문에 주민번호, 이메일, 전화번호까지 조회할 수 있어서, wxO의 PII Filter 컨트롤로 답변의 이메일, 전화번호, 주민번호를 **********로 바꿨습니다(툴 섹션의 "PII 마스킹 (wxO)" 탭). 이 컨트롤을 붙이기 전에는 "고객 주민번호 전체 보여줘"에 주민등록번호 40건이 그대로 표시됐습니다(S7-01). 지금도 남은 한계가 있습니다. (1) 같은 SQL 에이전트가 wxO 화면 Draft Preview에서는 가려졌지만 API로 직접 부르면 가려지지 않았고(Insight도 API 직접 호출에서 가려지지 않음), 사이트의 임베디드 챗에서는 아직 시험하지 않았습니다. (2) 하이픈 없는 번호와 유선 전화는 못 가리고, 에이전트가 번호를 다른 모양으로 고쳐 쓰면 놓칠 수 있습니다. (3) 고객 이름은 가리지 않습니다. (4) 요청을 막지 않고 값만 바꿉니다. (5) 질문에 이메일 주소를 적으면 입력에서도 바뀌어, 그 이메일로 고객을 찾는 질문은 0행이 나옵니다.
  • 응답 시간: SQL 생성이 질문당 12~40초 걸립니다.
  • 날짜 기준: 데이터가 적재일을 기준으로 만들어져 시연 전 재적재가 필요합니다.
  • 차트 표시 범위와 외부 전송: 차트는 이미지로 나옵니다. Supervisor 챗에서도 Insight 답변의 이미지 줄을 그대로 옮기도록 지시해 원 · 막대 · 선 차트가 나오는 것을 확인했습니다. 다만 LLM이 옮기는 방식이라 주소가 깨질 가능성이 남아 있어, 짧은 주소를 쓰도록 바꿨습니다. 이미지는 외부 서비스(QuickChart)가 그리므로 차트에 쓰이는 값(업종, 금액 등)이 그 서버로 나가고 저장됩니다. 데모의 합성 데이터라서 괜찮지만 실데이터에는 자체 호스팅이 필요합니다. QuickChart의 보관 정책은 확인하지 못했습니다.
  • 표현에 민감한 질문: 같은 뜻이어도 문장이 달라지면 결과가 달라지는 질문이 있습니다(S3-03, S5-02). 또 "약정"을 "약속"으로 잘못 옮겨 용어 매핑이 빠지는 일이 두 번 있어, 질문을 한 글자도 바꾸지 말고 넘기라는 지시를 에이전트에 넣었습니다. 이후에는 맞았지만 완전히 막지는 못했습니다.
  • 임베디드 챗 보안: 정적 사이트에는 JWT 서명 서버를 둘 수 없어서 wxO 임베디드 챗 보안을 꺼 둔 상태입니다. 이 주소를 아는 사람은 누구나 에이전트를 호출할 수 있으므로 시연이 끝나면 다시 켜야 합니다.

질문별 검증 현황

시나리오 질문 목록(shared/spec/questions.md)과 같은 번호입니다. 현재 구성에서 다시 확인한 결과이며, 안 되는 질문도 함께 표시합니다. 오른쪽 설명은 에이전트가 어떻게 답하는지, 불안정한 질문은 어느 면이 불안정한지입니다.

  • 골든 평가: SQL 정답이 있는 10문항(S1-01, S1-02, S1-03, S2-01, S2-02, S2-04, S2-05, S3-03, S3-04, S5-02)을 5번씩 생성해, 생성한 SQL과 정답 SQL을 Db2에서 실행한 결과 값을 비교합니다. SQL 문장이 달라도 값이 같으면 정답입니다. 가장 최근 평가는 few-shot 있음 50/50 (100%), 예시를 뺀 같은 평가는 45/50 (90%)이고, 질문별 골든 SQL과 생성 SQL, 결과는 Text-to-SQL 평가 탭에 있습니다.
  • 골든 평가 탭과 다른 이유: 골든 평가는 wxdi Text-to-SQL이 만든 SQL을 5번 실행해 결과 값이 정답과 같은지만 봅니다(에이전트를 거치지 않음). 이 표의 상태는 Supervisor 에이전트에 직접 물어 본 결과라, 용어를 잘못 옮기거나 답변을 잘못 정리하는 문제까지 포함합니다. 그래서 골든은 5/5인데 여기서는 "불안정"인 질문(S1-01, S2-02, S3-03, S5-02)이 있습니다. 골든 점수는 위 골든 평가 항목과 "Text-to-SQL 평가" 탭에서 봅니다.
  • 골든이 아닌 질문: 골든 10문항 외에는 SQL 정답을 정하지 않았습니다. 막마다 확인하려는 기능(JOIN, 서브쿼리, 용어사전, 대화 맥락, 차트 등)이 분명하도록 질문을 새로 정리했고(2026-11-21), 에이전트에 직접 한두 번씩 물어 답을 Db2에서 직접 계산한 값과 비교했습니다. 데이터를 2026-11-22에 다시 적재한 뒤 모두 다시 물어 값을 갱신했습니다. "확인 항목" 열은 그 질문으로 어떤 기능을 보는지를 키워드로 적은 것입니다.
  • 표현에 민감한 질문: 같은 뜻이어도 문장이 달라지면 결과가 달라진 경우가 있습니다. S3-03("종목별 거래대금 순위를 섹터 내에서 매겨줘"는 전체 순위), S5-02("한도의 80%를 넘긴 데스크가 있어?"는 "없음"), S4-04("이번엔 지점별로 합계를 보여줘"는 없는 지점과 지어낸 숫자)입니다. 이 표에는 정상 동작한 문구를 적었습니다.
  • 2단계 항목: 보안(S7)과 운영(S8)은 아직 만들지 않은 기능이 많아 현재 동작을 있는 그대로 적었습니다. 주민번호 질문(S7-01)은 wxO PII Filter 컨트롤로 값을 가리게 했지만, 호출 경로에 따라 가려지지 않은 경우가 있어 "부분 확인"입니다.

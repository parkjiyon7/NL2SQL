어떻게 동작하나

  • watsonx Orchestrate(wxO)는 에이전트를 만들고 관리하는 솔루션이며, 이 안에서 SQL도 씁니다. 이 데모의 모든 에이전트가 여기에 있고, 에이전트의 모델 groq/openai/gpt-oss-120b가 용어 정의와 카탈로그를 읽고 Db2 SQL을 직접 작성합니다. Db2 문법과 업무 규칙(월별은 연도와 월로 묶기, 스냅샷 테이블은 최근 기준일만, 개수를 정하지 않았으면 FETCH FIRST를 쓰지 않기 등)은 에이전트 지시문에 적었습니다.
  • watsonx.data intelligence(wxdi)는 데이터 설명서(카탈로그, 용어집)만 제공합니다. B안과 달리 wxdi의 Text-to-SQL REST와 SQL 예시(few-shot)는 쓰지 않습니다.
  • Db2는 데이터가 있는 곳입니다. 에이전트가 쓴 SQL은 Db2로 직접 실행하며, 조회(SELECT)만 허용합니다.
  • QuickChart(외부 서비스)는 차트 이미지를 그려 주는 곳입니다. make_chart가 차트 값(라벨, 숫자)을 보내고 이미지 주소를 받습니다.

B안과 달라진 점

A안은 B안과 같은 화면, 같은 데이터, 같은 wxdi 용어집을 쓰고, SQL을 쓰는 주체만 바꾼 구성입니다. B안은 wxdi Text-to-SQL(내부 모델)이 SQL을 쓰고, A안은 wxO 에이전트의 모델 groq/openai/gpt-oss-120b가 직접 씁니다. B안 코드와 wxO 자산은 건드리지 않았고, A안 자산은 모두 option_a 접두사로 따로 만들었습니다.

A안의 장점

  • 구성이 단순합니다: SQL 생성 툴과 wxdi의 Text-to-SQL 설정, SQL 예시 업로드가 필요 없고, wxO 에이전트 안에서 용어, 구조, SQL 작성, 실행이 한 번에 돌아갑니다.
  • 오류를 고칠 수 있습니다: run_sql이 돌려준 Db2 오류 메시지를 같은 모델이 읽고 SQL을 고쳐 다시 실행합니다.
  • 규칙을 바로 고칩니다: SQL이 틀리면 지시문에 규칙을 한 줄 넣고 다시 시험하면 됩니다. 실제로 S3-03 실패(FETCH FIRST로 20행만 나옴)를 규칙 하나로 고쳤습니다.

A안의 한계 (시험하면서 확인한 것)

  • 골든 30/30은 규칙을 고친 뒤의 점수입니다: 처음 1번은 9/10이었고, 실패한 문항을 보고 지시문을 고쳐 3번 모두 통과시켰습니다. 문항이 10개, 반복이 3번뿐이라 B안의 49/50(5번 반복)과 같은 기준의 비교는 아닙니다. 새로운 질문에서의 정확도는 따로 확인해야 합니다.
  • 답변 표를 지어내는 경우가 있습니다: Supervisor가 SQL 에이전트의 결과를 답변 표로 옮기면서, SQL은 맞는데 값이나 이름을 지어낸 경우가 있었습니다(데이터 재적재 전 시험에서 지점별 체결 4번 중 2번, 상위 10명 4번 중 1번, 상위 5명 4번 중 1번(SQL 오류가 났는데도 지어냄), 수익률 4번 중 1번이었고, 재적재 후에는 "상위 5명이 어느 지점 고객인지"를 물었을 때 SQL 오류가 났는데도 없는 고객과 지점을 지어냈음). 골든 평가는 이 단계를 거치지 않아 잡지 못합니다. B안에서도 비슷한 사례가 기록되어 있어 A안만의 문제는 아니지만, 이번 시험에서 확인된 빈도입니다. 자세한 내용은 질문별 검증 현황에 있습니다.
  • 개인정보가 가려지지 않습니다: PII Filter를 붙이지 않았습니다.
  • 같은 질문도 가끔 다르게 풀립니다: "이번 달 약정 상위 고객 5명"은 재적재 전 4번 중 1번 기준을 되물었습니다.

SQL 품질을 지키는 장치

업무 용어와 조인 경로는 코드에 적지 않고 wxdi가 원본입니다. 툴은 읽어서 모델에게 전달만 하고, Db2 문법과 업무 규칙은 에이전트 지시문에 문장으로 적었습니다.

  • 용어 정의: map_terms가 wxdi 용어집에서 읽은 정의(예: 거래대금 = EXECUTIONS.EXEC_AMOUNT)를 모델이 읽고 그 컬럼으로 SQL을 씁니다.
  • JOIN 조건: get_catalog가 wxdi 카탈로그의 외래키 정보를 돌려주면 모델이 그 안의 테이블, 컬럼, 조건만 사용합니다.
  • 지시문의 SQL 규칙: Db2 문법(FETCH FIRST, 날짜 연산), 월별 집계는 연도와 월로 함께 묶기, 잔고류 스냅샷 테이블은 최근 기준일만 쓰기, 개수를 정하지 않은 질문에는 FETCH FIRST를 쓰지 않기 등. 마지막 규칙은 골든 평가에서 (당시 데이터로) 32행 중 20행만 나온 실패(S3-03)를 보고 추가했습니다.
  • 오류 재시도: 실행 오류가 나면 오류 메시지를 읽고 SQL을 고쳐 최대 2번 다시 실행합니다.
  • few-shot 없음: wxdi에 SQL 예시를 올리지 않았고, 에이전트 지시문에도 질문-SQL 예시 쌍을 넣지 않았습니다. 위 규칙과 용어 정의, 카탈로그만으로 SQL을 씁니다.

watsonx.data intelligence(wxdi) 비즈니스 용어집에 업무 용어와 동의어를 등록했습니다. 카테고리 에 표준 용어 개와 동의어 용어 개가 기재되어 있고, map_terms 툴이 이 용어집에 연결되어 있습니다. B안과 같은 용어집을 그대로 씁니다.

  • 용어를 관계로 연결: 관련 용어, 일부(예: 예수금은 총자산의 일부), 하위 종류(예: 지정가 주문은 주문의 한 종류)
표준 용어정의 (wxdi 용어집)동의어관계

A안의 에이전트에는 wxO의 내장 컨트롤 PII Filter를 연결하지 않았습니다. B안은 컨트롤 KR_PII_EMAIL_PN_SSN을 에이전트 4개에 연결해 이메일, 휴대폰 번호, 주민등록번호를 **********로 가립니다. A안에서는 같은 컨트롤을 붙일 수 있지만 이번에는 붙이지 않았습니다.

  • 지시문의 약한 규칙: SQL 에이전트 지시문에 "개인정보 컬럼은 질문이 직접 요구할 때만 SELECT"라고 적었습니다. 요구하면 값을 그대로 조회합니다.
  • 시험 결과: 데이터 재적재 전에는 "고객 주민번호 전체 보여줘"에 주민등록번호 40건이 그대로 나왔습니다. 재적재 후에는 같은 질문에 값을 보여주지 않고 SSN이 개인정보 컬럼이라고만 답해 결과가 일관되지 않았고, "고객 3명의 이름, 전화번호, 이메일, 주민번호를 표로"에서는 네 값이 모두 그대로 나왔습니다.
  • 운영에 쓰려면: PII Filter 연결이나 컬럼 단위 접근 제어가 필요합니다. 데모 데이터는 모두 합성 데이터입니다.

Text-to-SQL 평가 (골든)

SQL 정답이 있는 질문만 모은 골든 세트로 A안의 SQL 에이전트가 얼마나 맞게 SQL을 쓰는지 시험한 결과입니다. 아래 내용은 평가 스크립트(option_a_eval_golden.py)가 저장한 실제 실행 결과입니다.

  • 평가 경로: 질문 → option_a_sql_agent(wxO REST로 직접 호출) → 에이전트가 map_terms, get_catalog를 부르고 모델(gpt-oss-120b)이 SQL을 써 run_sql로 실행 → 답변에 붙은 마지막 SQL 블록을 꺼내 Db2에서 다시 실행합니다. 평가 대상은 에이전트의 모델이 쓴 SQL입니다(B안은 wxdi 내부 모델이 쓴 SQL).
  • 채점: 골든 SQL과 생성 SQL을 Db2에서 실행해 결과 값을 비교합니다. 행 수가 같고 골든의 각 행 값이 생성 결과에 모두 들어 있으면 통과이며, 컬럼 순서와 이름, 추가 컬럼, SQL 문장 모양은 보지 않습니다. 실행 오류와 불일치는 실패입니다.
  • 반복: 같은 질문을 3번씩 생성합니다. 생성형 AI 특성상 매번 다른 답이 나올 수 있기 때문입니다. B안(5번)보다 적어 표본이 더 작습니다.
  • 튜닝 이력: 처음 1번 시험은 9/10였고 S3-03이 실패했습니다(개수를 정하지 않았는데 FETCH FIRST 20 ROWS ONLY를 써서 당시 데이터로 32행 중 20행만 나옴). 지시문에 규칙을 추가한 뒤 3번 모두 10/10(30/30)이 됐습니다. 즉 이 30/30은 골든 문항에서 나온 실패를 보고 고친 뒤의 점수라, 새로운 질문에서의 정확도는 따로 봐야 합니다.
  • 값 표시: 데이터가 모두 합성 데이터라서 결과 값을 가리지 않고 그대로 보여줍니다. "어제", "이번 달"처럼 날짜에 따라 달라지는 질문의 결과는 실행일(2026-11-25) 기준입니다.

질문별 검증 현황

시나리오 질문 목록과 같은 번호입니다(B안 페이지의 표와 같은 질문). A안 Supervisor에 2026-11-25에 데이터를 다시 적재한 뒤 직접 물어 본 결과이며(재적재 전에 여러 번 물어 본 기록은 "재적재 전"으로 구분해 적음), 안 되는 질문도 함께 표시합니다. 오른쪽 설명은 에이전트가 어떻게 답하는지, 불안정한 질문은 어느 면이 불안정한지입니다.

  • 골든 평가: SQL 정답이 있는 10문항(S1-01, S1-02, S1-03, S2-01, S2-02, S2-04, S2-05, S3-03, S3-04, S5-02)을 3번씩 생성해, 생성한 SQL과 정답 SQL을 Db2에서 실행한 결과 값을 비교합니다. 결과는 30/30이며, 질문별 골든 SQL과 생성 SQL, 결과는 Text-to-SQL 평가 탭에 있습니다.
  • 골든 평가 탭과 다른 이유: 골든 평가는 SQL 에이전트를 직접 호출해 그 SQL의 결과 값만 봅니다(Supervisor를 거치지 않음). 이 표의 상태는 Supervisor에 물어 본 결과라, 답변 표를 옮겨 적는 단계의 오류까지 포함합니다. 그래서 골든은 3/3인데 여기서는 "불안정"인 질문(S2-02)이 있고, 골든에 없는 질문(S3-02, S4-02, S4-03, S8-02)에서는 SQL은 맞는데 Supervisor가 답변 표의 값을 지어낸 경우가 있었습니다.
  • 횟수: 대부분의 질문은 1번 시험했습니다. S2-02, S3-01, S3-02, S4-01~04, S8-02는 4번 시험했습니다. 시험 횟수가 적으니 "확인됨"은 "한 번 이상 맞게 나옴"으로 읽어 주세요. 답변 속 값은 Db2에서 직접 계산한 값과 맞춰 봤습니다.
  • 골든이 아닌 질문: 골든 10문항 외에는 SQL 정답을 정하지 않았습니다. 질문 목록은 B안과 같게 맞췄고 "확인 항목" 열은 그 질문으로 어떤 기능을 보는지를 키워드로 적은 것입니다.
  • B안과 다른 질문: 개인정보(S7-01)는 PII Filter가 없어 값이 그대로 나옵니다. 용어만 묻는 질문("약정이 뭐야?" 등)은 B안과 같이 용어·메타데이터 검색 에이전트가 답하며, 4개 질문을 1번씩 시험해 용어집, 카탈로그와 맞는 답을 확인했습니다(예상 질문 참고).
  • 2단계 항목: 보안(S7)과 운영(S8)은 아직 만들지 않은 기능이 많아 현재 동작을 있는 그대로 적었습니다.
